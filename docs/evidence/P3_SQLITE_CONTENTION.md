# P3: cross-process SQLite lock contention vs corruption

Original tests-only PR #23 commit `851726cd1d12d43e2270ea0035e6113f49218597` reproduced the defect on the unchanged eight OS/Node CI matrix. Real second-process schema initialization while a separate SQLite writer holds WAL `BEGIN IMMEDIATE` returns `Error: database is locked`. The original constructor incorrectly labels this `CACHE_CORRUPTED` and suggests deleting the healthy database. See [original RED push workflow](https://github.com/levencode-labs/blastradius/actions/runs/45156045867), Ubuntu 24.04 Node22 job 137629098220. Negative test: unsupported schema version remains corruption.

Fix only classification of explicit SQLite `BUSY`/`LOCKED` signals as `CACHE_BUSY` with non-destructive retry guidance; still close a failed open connection. Pass through the stable MCP error code. All other errors, schema incompatibility and actual broken JSON remain `CACHE_CORRUPTED`. This change does **not** assert arbitrary simultaneous writes will always succeed; it prevents false data-loss advice and tests reopening after the write lock releases. No migration, schema/lockfile change, global config edit, publish or release. Full cross-platform/byte-parity and exact-head/merge-SHA acceptance required.
